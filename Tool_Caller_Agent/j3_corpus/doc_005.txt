**SOC Runbook Excerpt: Triage Workflow for Phishing Email Reported by Employee**

## Header Analysis Steps

Upon receiving a report from an employee regarding a potential phishing email, the SOC team should immediately begin the triage process to determine the severity of the threat and assess whether any actions need to be taken. The following steps outline the initial analysis:

1. **Gather Information**: Record all relevant details provided by the reporting user, including:
   - Employee's name
   - Date and time of the email receipt
   - Sender’s address (if available)
   - Subject line of the email
   - Brief summary of content
2. **Header Analysis**: Extract and analyze the email headers to identify any discrepancies or anomalies that might indicate a phishing attempt:
   - `X-Mailer`: Verify if it is standard or unusual.
   - `Received-SPF`, `DKIM`, `DMARC` records: Check for valid SPF, DKIM, and DMARC policies.
   - `Return-Path`: Ensure it matches the sender's address.
3. **Detect Indicators of Compromise (IoCs)**: Look for any IoCs within the email headers that might suggest a phishing attempt:
   - Suspicious IP addresses or domain names
   - Unusual timestamps
4. **Cross-reference with Known Threats**: Use threat intelligence feeds to cross-check the sender's address, domain names, and URLs against known phishing campaigns.

## Attachment Sandboxing Procedure

If the email contains any attachments, they must be handled carefully to avoid potential infection of the SOC environment:

1. **Isolation**: Place the attachment in a sandboxed environment that is isolated from other systems.
2. **File Analysis**: Use automated tools for static and dynamic analysis:
   - Static analysis: Scan for known malware signatures using antivirus software.
   - Dynamic analysis: Execute the file in a controlled environment to monitor behavior without executing harmful code.
3. **Behavioral Monitoring**: Monitor any network traffic generated by the attachment, looking for connections to known malicious IP addresses or domains.
4. **Reporting Findings**: Document all findings from the sandboxing process and share them with the incident response team.
